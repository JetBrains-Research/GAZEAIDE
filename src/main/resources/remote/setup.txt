CONNECT LATER
You do not need a storage account now. Leave Enable remote upload unchecked. Editing settings or opening this dialog sends nothing. Save connection does not contact the receiver, although IDE password storage may ask for permission.

GOOGLE DRIVE — RESEARCHER SETUP
This is an Apps Script connector, not built-in Google OAuth sign-in or a connection made by pasting a Drive folder link.
1. Use an institution-approved Google account and create a private destination folder. Do not share it publicly or with participants.
2. Save the receiver template with the button below. In a new Google Apps Script project, paste its contents into Code.gs.
3. In Project Settings → Script Properties, set STUDY_ID, FOLDER_ID and PARTICIPANTS_JSON. The latter maps participant codes to separate random upload tokens, for example {"P01":"64-random-hex-characters"}. Generate a genuinely random token for each participant (for example: openssl rand -hex 32); do not use that example text as a token.
4. Deploy → New deployment → Web app. Execute as the researcher. Allow access without Google sign-in (usually Anyone). The template validates a participant token before accessing the folder. The researcher authorizes the script's Google Drive access; the plugin receives no Google password or Google access token. Use a dedicated approved study account where possible. If institutional policy disallows this deployment, use an approved HTTPS research server instead.
5. In this dialog, select Google Drive and paste the deployed web app /exec address. Enter matching study/participant codes and that participant's upload token. Never distribute the whole token list, folder access or an admin credential.
6. Acknowledge the notice, enable uploads, Save connection, and Test connection. This sends a test message with the configured study/participant codes and a new random upload ID, without recording events, and checks authentication and folder lookup; it writes no recording. Then record a synthetic session, preview and upload it. Verify the resulting JSON, duplicates/retry, unauthorized access, withdrawal/deletion and retention before using real participant data.
7. Remove a participant's entry in PARTICIPANTS_JSON to revoke future uploads. Deleting their uploaded files and applying retention/backup rules are separate researcher actions. A token holder can submit data for that participant code, so keep tokens private.

The provided receiver has no read/list API for participants. Files remain private under the Drive account's permissions. Google/Apps Script logs, account recovery, quotas, storage location, retention and terms need institutional review; the template makes no residency guarantee. Anonymous deployment is still a public endpoint and may be unsuitable for larger or sensitive studies. A managed API can add stronger authentication and rate limits. Apps Script responses redirect to Google's content host; the plugin fetches the acknowledgement without forwarding the token.

OTHER STORAGE — HTTPS RECEIVER PROTOCOL
Provide a private server-side upload endpoint. Do not connect a database directly from the plugin or distribute database/admin credentials. Supabase, S3 and institutional databases can sit behind this API.
POST application/json over HTTPS with Authorization: Bearer <participant-token> and the reduced payload shown in Preview. Google Drive mode instead sends {"token":"...","payload":{...}} because Apps Script does not expose arbitrary request headers to doPost.
The receiver must authenticate study + participant, validate an explicit allowlist schema (including all nested objects), enforce payload limits, store by uploadId without overwriting different content, and acknowledge only after durable storage with {"ok":true,"uploadId":"the same UUID"}. For kind=connection_test, validate the connection and return that acknowledgement without storing a participant session. The included Drive template is a reference implementation of the schema. Reject malformed, unauthorized or unexpected fields. Do not echo/log tokens or payloads.
Generic connectors do not follow redirects. Use the final HTTPS endpoint, without query-string secrets. Payload limit is 8 MiB, 50,000 viewing events and 5,000 configuration changes; longer recordings remain local and require a revised upload design, never silent truncation.

LOCAL QUEUE AND AUTOMATION
Automatic upload is off by default. When enabled before Start recording, it makes one attempt after that recording stops; it never uploads past recordings in bulk. Failures stay in the local reduced-data queue. Retry pending uploads is explicit; nothing retries on startup or a timer. Only entries bound to the same connector, address, study and participant can be retried. Changing the task code does not relabel an already queued recording. Delete pending uploads affects local unsent payloads only. Disconnect disables uploads and removes this connection's stored token; it does not delete cloud files. The native AI handoff is an independent data flow.
